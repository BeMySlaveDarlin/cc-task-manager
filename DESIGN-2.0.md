# cc-task-manager 2.0 — дизайн

Статус: черновик на обсуждение. Дата: 2026-07-23.

## 1. Что не так с 1.2.0

### 1.1 Синхронизация с нативным стором не работает вообще

Скиллы завязаны на `.claude/tasks/tasks.json` в корне проекта (`ts:180`, `rs:24`, `finalize:22`).
Такого файла не существует ни в одной версии Claude Code. Проверено:

- в бандле CLI 2.1.218 строки `.claude/tasks/tasks.json` нет; единственный `*tasks.json` — `scheduled_tasks.json` (cron)
- на диске нет ни одного `<project>/.claude/tasks/`

Реальный стор:

```
~/.claude/tasks/session-<первые 8 символов session-id>/<N>.json
~/.claude/tasks/<полный session-uuid>/<N>.json          # старый формат, 51 директория из 246
```

Формат записи:

```json
{
  "id": "4",
  "subject": "Playwright-демо фильтра инвайтов",
  "description": "Поднять фронт локально, залогиниться...",
  "activeForm": "Демонстрирую фильтр в Playwright",
  "status": "completed",
  "blocks": [],
  "blockedBy": []
}
```

Все шаги «сверка с нативным стором» уходят в no-op: файла нет → шаг молча пропущен.
Задача #2 закрыта как выполненная, но чинила несуществующий путь.

Связь «проект → его нативные задачи» восстанавливается детерминированно:
`~/.claude/projects/<cwd с / заменёнными на ->/<uuid>.jsonl` → `uuid[:8]` → директория стора.
В env любого bash-вызова есть `CLAUDE_CODE_SESSION_ID`.

Масштаб фичи: 246 директорий стора, из них с задачами — 28, всего 163 задачи (~11% сессий).
Тулы `Task*` доступны не всегда, судя по всему привязаны к agent teams
(`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`, в payload хуков `teammate_name`/`team_name`).
Вывод: синк чинит редкий, но болезненный класс расхождений — он не главная ценность 2.0.

### 1.2 Состояние размазано по четырём местам

Одна задача = имя файла (`open-|done-` + NN + slug) + frontmatter + строка в `tasks.md`
(в одной из 2–3 таблиц) + иногда абзац в `queue.md`. Смена статуса требует четырёх
согласованных правок без единого механизма проверки. Модель делает три из четырёх.

### 1.3 Статус в имени файла

Самое дорогое решение: rename требует Bash (промпт на разрешение), точного знания
сгенерированного slug, ломает `[[ссылки]]` и `external_id`-указатели. Статус уже во frontmatter.

### 1.4 `tasks.md` — производная, поддерживаемая вручную

Полностью восстановим из frontmatter'ов, но по инструкции патчится построчно.
Правило `ts:265` «молча восстанови консистентность» не содержит алгоритма разрешения конфликта.

### 1.5 `queue.md` — сущность без определения

Ни формата, ни примера, ни парсера. В репозитории плагина файла нет.

### 1.6 Один алгоритм описан трижды

Сверка расписана в `ts` (три случая расхождений), `rs` (два), `finalize` (свой перенос) —
разными словами. Дрейф уже произошёл.

### 1.7 Мелочи

- дата «из системного контекста» (`ts:261`) → галлюцинации; нужен `date +%F`
- следующий id из `tasks.md`; если протух — дубль номера
- `NN` двузначный → сортировка ломается на 100+
- AskUserQuestion на `close` — трение на самой частой операции (close не деструктивен)
- нет шага верификации после операции

### 1.8 Про JSON сам по себе

Переезд формата ничего не чинит, если писать его продолжает модель: битое экранирование
многострочного текста = стор не парсится совсем, тогда как кривой md деградирует мягко.
JSON окупается ровно тогда, когда его пишет и читает код.

## 2. Решение

`<plugin>/bin` автоматически попадает в PATH (проверено в env: путь плагина в PATH есть,
хотя самой директории ещё нет). Значит `bin/cctm` вызывается как обычная команда,
без `${CLAUDE_PLUGIN_ROOT}`, из любого проекта.

Разделение ответственности:

| Кто | За что отвечает |
|-----|-----------------|
| `cctm` (python3) | состояние, инварианты, синк, атомарность |
| Скилл (модель) | понять фразу, выбрать команду, написать текст задачи |

Модель больше не поддерживает денормализованные данные.

## 3. Модель данных

### 3.1 Структура

```
.claude/session/
  meta.json          {"version": 2, "next_id": 8}
  tasks/
    007.json         вся задача целиком
    118.json
  .lock
```

Никаких `tasks.md`, `queue.md`, `details/`, frontmatter. Ни одного markdown-файла в сторе.

**Индекса нет сознательно.** Отдельный `index.json` — денормализация, которая воспроизводит
болезнь 1.2.0 (два источника → рассинхрон → doctor → «починил один, забыл второй»).
Список строится на лету чтением `tasks/*.json`: 118 файлов по ~2 КБ — единицы миллисекунд,
кэшировать нечего.

`meta.json` индексом не является: хранит только счётчик и версию схемы, данные задач не дублирует.
Максимальная авария — пропущенный номер, что безвредно. `next_id` монотонный,
id удалённых задач не переиспользуются.

**Имя файла — только id.** Без slug: slug в имени — ещё одно место для рассинхрона и повод
для rename. Файл не переименовывается никогда за всю жизнь задачи.

### 3.2 Формат задачи

```json
{
  "id": 7,
  "title": "Добавить middleware авторизации",
  "status": "open",
  "priority": "HIGH",
  "order": 3,
  "created": "2026-07-20",
  "updated": "2026-07-23",
  "closed": null,
  "blockedBy": [4],
  "tags": ["auth"],
  "external": { "session": "session-8d52e8a1", "id": "4" },
  "body": {
    "description": "Что нужно сделать.",
    "context": "Откуда пришла задача, связанные файлы.",
    "plan": ["Шаг 1", "Шаг 2"],
    "verify": "Команда или критерий готовности.",
    "result": null,
    "files": []
  }
}
```

- `status`: `open` | `deferred` | `done`
- `order`: позиция в очереди — заменяет `queue.md`
- `external`: связь с нативным стором вместо строкового `external_id`
- `body.result` и `body.files` заполняются при закрытии (что сделано, какие файлы затронуты)

### 3.3 Как модель пишет тело

Проблема, которую решаем: модель не должна генерировать JSON руками — многострочный текст
с кавычками и переводами строк это главный источник битого стора.

Основной путь — markdown-времянка, которую модель пишет привычным `Write`, а скрипт
разбирает по заголовкам в поля `body`:

```
$ cctm create --title "Добавить middleware авторизации" --priority HIGH
#7 создана

# модель пишет /tmp/.../body.md через Write:
#   ## Описание ... ## Контекст ... ## План ... ## Как проверить ...

$ cctm set 7 --md /tmp/.../body.md
#7 обновлена
```

Скрипт нормализует markdown → JSON, экранирование делает `json.dump`. Обратно:
`cctm show 7 --md` рендерит тело в markdown.

Альтернативы: `cctm set 7 --md -` (stdin, heredoc) и `cctm set 7 --json FILE`
для точечных правок. Неизвестные заголовки складываются в `body.notes`, а не теряются.

## 4. CLI-контракт

Все команды работают в cwd проекта. Вывод по умолчанию — компактный текст, `--json` — для разбора.

```
cctm init                                  # создать .claude/session/
cctm list [--status open|done|deferred|all] [--priority P] [--tag T] [--json]
cctm next [--json]                         # что делать дальше: open, сортировка priority+order
cctm show <id> [--md|--json]
cctm grep <pattern> [--json]               # поиск по телам задач (заменяет grep по details/)
cctm create --title T [--priority P] [--tags a,b] [--blocked-by N] [--order N]
cctm set <id> [--md FILE|-] [--json FILE]  # тело задачи
cctm update <id> [--title T] [--priority P] [--status S] [--tags a,b] [--blocked-by N] [--order N]
cctm close <id> [--md FILE|-]              # тело закрытия: result, files
cctm reopen <id>
cctm delete <id> --force
cctm sync [--dry-run] [--session ID] [--quiet]
cctm doctor [--fix]
cctm export --md [--out FILE]              # разовый человекочитаемый дамп, не артефакт стора
cctm migrate [--dry-run] [--path DIR]
```

## 5. Синхронизация с нативным стором

`cctm sync`:

1. Определяет сессии проекта: `~/.claude/projects/<slug(cwd)>/*.jsonl` → список uuid.
2. Для каждого uuid ищет `~/.claude/tasks/session-<uuid[:8]>/` и `~/.claude/tasks/<uuid>/`.
3. По умолчанию берёт текущую сессию (`CLAUDE_CODE_SESSION_ID`) + сессии с mtime новее
   последнего синка. `--session ID` — принудительно.
4. Мерж:

| Ситуация | Действие |
|----------|----------|
| есть `external`-связь, натив `completed`, реестр `open` | закрыть в реестре |
| нет связи, натив `completed`, заголовок матчится (нормализация + ratio ≥ 0.85) | связать + закрыть |
| нет связи, натив любой, матча нет | создать запись со статусом из натива |
| натив `pending`, реестр `done` | реестр прав, не трогать, упомянуть в отчёте |

5. `--dry-run` печатает план без записи.

**Обязательное правило:** если стор не найден — печатать явно, с проверенными путями.
Молчаливый no-op — то, что убило 1.2.0.

Формат директорий стора недокументирован и уже менялся. Скрипт поддерживает оба варианта
и деградирует явным сообщением, а не тишиной.

## 6. Хуки

`hooks/hooks.json` в плагине:

| Событие | Команда | Зачем |
|---------|---------|-------|
| `TaskCompleted` | `cctm sync --quiet --from-hook` | закрытие нативной задачи сразу попадает в реестр |
| `SessionEnd` | `cctm sync --quiet --from-hook` | подбирает хвост оборванной сессии |

`TaskCreated` сознательно не вешаем: черновики нативного todo-списка засорят реестр.

Payload приходит в stdin JSON (`hook_event_name`, `task_id`, `task_subject`,
`task_description`, `cwd`, `session_id`) — читается при `--from-hook`.

Предохранители:

- если `.claude/session/` в cwd нет — no-op (проект не использует плагин)
- `flock` на `.claude/session/.lock` — несколько сессий в одном проекте
- атомарная запись: tmp + `os.replace`, пофайлово
- `--quiet`: в stdout ничего, кроме ошибок

## 7. Скиллы после переезда

| Скилл | Было | Станет | Содержание |
|-------|------|--------|------------|
| `ts` | 265 строк | ~60 | таблица «фраза → команда cctm», шаблон тела задачи, подтверждение только на `delete` |
| `rs` | 94 | ~30 | `cctm next` → показать → спросить с чего начать |
| `finalize` | 173 | ~60 | `cctm sync` → `close` сделанного → `create` нового → `finalize.local.md` → отчёт |

Протокол хранилища исчезает из скиллов — он в коде, в одном экземпляре.

Отдельное правило во всех трёх: **если `cctm` недоступен — сообщить, что нужно обновить
плагин, и остановиться.** Не ковырять стор руками.

Подтверждения: `close` — молча (обратимо через `reopen`), `delete` — через AskUserQuestion.

## 8. Миграция

Масштаб: 18 проектов, ~500 detail-файлов (максимум — 118 в `Algo/lms`),
плюс глобальный реестр `~/.claude/session/` (37 задач).

`cctm migrate`:

1. бэкап `.claude/session/` → `.claude/session.bak-YYYYMMDD/` (всегда, безусловно)
2. парсит `details/{open,done}-NN-slug.md`: frontmatter → поля записи, разделы тела → `body.*`
3. задачи, которые есть только в таблицах `tasks.md` → записи с пустым телом и пометкой в `body.notes`
4. `external_id` (строка `T-NNN`) → `external: {session: null, id: "NNN"}`, помечается unverified
5. `queue.md` целиком уходит в бэкап; его содержимое печатается в вывод с пометкой
   «схлопни в тела задач при следующем /finalize» — автоматически разнести по смыслу нельзя
6. старые `tasks.md`, `queue.md`, `details/` удаляются из `.claude/session/` (копии в бэкапе)
7. `--dry-run` — план без изменений

Ссылки на старые имена файлов (`details/open-NN-slug.md`) могли попасть в CLAUDE.md, memory,
ADR других проектов. `migrate` печатает список удалённых путей, чтобы прогнать `grep`.

## 9. Инварианты `cctm doctor`

1. каждый `tasks/*.json` парсится, имя файла == `id` внутри
2. `id` уникальны, `meta.next_id` > max(id)
3. `blockedBy` ссылается на существующие id, циклов нет
4. `status`/`priority` из допустимого множества, даты валидны
5. `closed` заполнен ⟺ `status == done`
6. `external.session` существует на диске (инфо, не ошибка)

`--fix` чинит 2, 5; остальное — отчёт. Инварианта «индекс ↔ файлы» больше не существует —
он устранён архитектурно, а не проверкой.

## 10. Совместимость и риски

| Риск | Митигация |
|------|-----------|
| формат нативного стора недокументирован, менялся | поддержка двух вариантов, явное сообщение при промахе |
| Windows native: `bin/cctm` без расширения | shebang + `cctm.cmd`-шим; на WSL не блокер |
| legacy `install.sh` не кладёт `bin` в PATH | симлинк `bin/cctm` → `~/.local/bin/cctm` |
| стор больше не читается глазами и грепом | `cctm show --md`, `cctm grep`, `cctm export --md` |
| внешние читатели (Atlas, задача #37) ждали `tasks.md` | контракт с Atlas переводится на JSON — для него это проще |
| python3 отсутствует | заявить в требованиях; есть везде, где живёт Claude Code |

Версия: **2.0.0**, ломающая.
